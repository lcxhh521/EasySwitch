# 测试范围与运行方法

2026-10-18 更新。唯一需求清单为 BACKLOG.md。B115已取消任务派发、规则/评价/建议、并行互审、EasySwitch MCP互调与自动注册，以及专用后台执行器；不再规划替代调度路线。历史设计只保留在Git历史，用户已有记录和规则文件不删除、不迁移、不自动执行。


项目有两个测试入口，结果不能互相替代。通过本地白名单，只说明经过审计的纯函数、假服务和假程序用例通过，不能据此声称真实客户端、macOS 系统行为或真实账号已经验收。

## 日常开发：受控本地测试

需要 Node.js 22.18 或更新版本。通常运行：

```sh
npm run typecheck
npm run test:local
node --check web/app.js
node --check web/controls.js
git diff --check
```

`npm run test:local` 执行 `bin/test-local.ts` 中逐文件列出的白名单，不会展开 `core/test/*.test.ts`。清单是唯一运行依据；本页按能力解释范围，不复制一份容易过期的文件清单。

这个入口会：

- 创建临时 HOME、USERPROFILE 和应用数据目录，强制使用内存密钥库，结束后清理自己的目录
- 预加载 `core/test/local-only-guard.ts`，限制 HTTP、HTTPS、HTTP/2、fetch、TLS 和原始 TCP 的出站目的地；拒绝外部主机和 Unix socket 路径
- 在 HTTP 原始目标层也检查地址，包括直接构造 ClientRequest，避免环境代理把外部请求改成 loopback socket 后绕过限制；localhost 只解析为固定环回地址
- 阻止一般子进程执行，不允许真实 agent、浏览器登录或系统钥匙串调用
- 对少数混合文件显式跳过真实程序测试；桌面假程序单独运行，并按固定内容哈希允许已审阅的脚本

报告可靠性：白名单文件逐个在独立 Node 进程中直接执行，保留 `--test-force-exit`。官方 custom reporter 把结构化结果和结束标记写入每文件的临时报告；Node 关闭报告文件后才退出。父入口同时检查退出状态、完整 JSON、文件身份、顶层计划与结果编号、失败与取消。缺失或损坏的报告一律失败，不能只凭退出码 0 或终端的绿色行判断通过。终端最后的 `Local test totals` 是已验证报告的总数；出现 `INCOMPLETE` 表示整轮失败。每文件有 120 秒上限，超时也失败。

逐文件执行避免 Node 24.19 的并行 `child-v8` stdout 尾部在强制退出时丢失；只给原多文件 runner 加报告文件或限制并发，不能保证内部结果管道完整。测试进程固定设置 `NODE_TEST_CONTEXT=easyswitch-local`，仅维持已有 fixture/内存凭据判断；不继承调用方环境，不改变网络、子进程或桌面脚本哈希保护。

这些是 JavaScript 测试预加载保护，不是操作系统级网络或文件系统沙箱。不要把未经审计的脚本、原生扩展或任意测试文件加入清单。原生代码、手动 DNS/UDP、已有外部文件描述符等需要额外审查，不能仅凭预加载保护推断安全。

真实 Keychain 用例默认跳过。看到 `skip` 不能记成通过；测试进程默认内存存储，也不等于真实钥匙串已经验证。

保护本身由 `local-only-guard.test.ts` 检查。外部主机的拒绝测试使用假的底层连接器，先证明不会到达连接步骤，不会为了证明拦截有效而尝试连接真实外部服务。

## 完整套件：需要受控的真实环境

`npm test` 实际运行：

```sh
node --test --test-force-exit core/test/*.test.ts
```

它包含所有匹配文件，其中一些会发现或启动本机已安装程序、读取实际客户端配置、查询登录状态、运行工具回合，或检查系统进程。某些程序没安装时会跳过；程序一旦安装，相同命令就可能进入真实路径。因此不能用“这台机器应该没装”代替审计，也不能在仅允许 fake 测试的环境直接运行它。

以下文件仍需与纯本地验收区分：

- `chatgpt-e2e.test.ts`：真实 app-server 路径；文件级初始化也可能执行模型发现，跳过单个测试体仍不够
- `claude-e2e.test.ts`、`codex-e2e.test.ts`：真实客户端工具回合、目录发现及实际配置检查
- `agent-launch.test.ts`、`es-cli.test.ts`：真实交互启动器、命令行进程与会话清理
- `accounts.test.ts`、`efforts.test.ts`：包含真实账号目录或已安装程序的帮助/档位发现
- `chatgpt-launcher.test.ts`：包含 shell 脚本、真实进程参数和程序发现检查
- `ledger.test.ts`：五项纯数据/文件断言已审计加入；图标清单生成用例会启动脚本，在本地入口按精确测试名称排除，不是通过

完整验收应在明确允许真实程序操作的环境进行，事先确认会触及哪些安装、配置、登录和工具权限。`EASYSWITCH_TEST_KEYCHAIN=1` 只应在另行安排的 macOS 验收中使用；它允许真实的独立测试条目读、写、更新和删除，不应作为常规测试变量。

真实客户端指向假上游，仍然是真实客户端验收。即使假上游不产生模型费用，客户端的自动更新、登录刷新、插件、hooks、文件访问和工具执行仍需单独控制。真实供应商调用和付费行为也不由 `npm test` 这个命令自动授权。

## 改哪些代码，就同步检查哪些断言

### 网关认证与桌面边界

本地覆盖看 `gateway-auth*`、`server-auth-persistence`、`server-security`、`chatgpt-boundary`、`gateway-upgrade`。必须同时检查完整套件中的 Claude、Codex、ChatGPT 和 `es` 请求是否仍使用真正签发、来源正确的 capability。

- 令牌格式可读不等于认证有效；假客户端也要通过自己的测试 authority 签发
- 外接模型和合并本地目录需要本地权限，原生厂商登录只授权其固定厂商路径
- 重启、过期、撤销、错误的权限范围都要有负例
- 不得给所有测试自动补令牌，从而掩盖匿名请求应该被拒绝的事实
- 合并模型目录的缓存验证器要覆盖实际名称、档位和原生目录字段变化，不能只比较模型 ID；`chatgpt-boundary` 用 loopback 假目录验证这些变化，以及键/目录顺序和顶层传输时间戳不造成无谓失效

### 启动接口与清理

取命令的断言应使用命令准备接口和注入的程序发现、模型目录、登录状态。真正启动接口必须使用 fake 运行时；把旧 GET 改成 POST 后直接调用真实 Terminal，会产生测试外的副作用。

检查目录清理之外，还要检查对应会话撤销、启动失败、信号终止和清理失败，并确认其他会话没有被撤销。`es models` 应断言实际返回模型及错误处理，不能把 401 后的空输出当成成功。

`es-cli-local.test.ts` 使用注入的子进程和本地 API 验证这些边界；它不替代 `es-cli.test.ts` 的真实客户端回合。



### macOS 路径

涉及实际文件存在性、符号链接、目录前缀或隔离边界的新 fixture，先规范化系统临时目录：

```ts
const root = mkdtempSync(join(realpathSync(tmpdir()), "es-fixture-"));
t.after(() => rmSync(root, { recursive: true, force: true }));
```

macOS 可能把路径显示成 `/var/...` 或 `/private/var/...`。不要删掉隔离断言来回避路径差异；对真实路径统一解析后再比较。仅测试配置字符串时使用的字面量 `/tmp/session` 不代表真实目录，无需混为一谈。

“没改用户配置”的本地测试应使用拥有明确初始字节的私有 sentinel 文件。只检查真实配置里没有几个产品关键词，不能证明字节没变，也不能把观察到的变化自动归因于其他应用。

### 协议和数据回归

本地假服务必须覆盖当前生产路由，而非只测试已经不再调用的转换器：

- thinking 先到、文字后到时，客户端是否在上游结束前收到增量
- 工具结果内容块、孤儿工具调用、system/developer 指令和供应商自带工具
- 第三方 Messages 来源的字段清理，以及跨协议错误的可读性和脱敏
- 中途失败已经产生的用量，预算重启恢复和未知费用
- 模型来源导入、方案恢复、定价优先级，以及本地假 OAuth 的状态、nonce、刷新和注销

相关纯测试包括 `outbound-shape`、`protocol-streaming`、`source-adapters`、`protocol-safety`、预算测试，以及 `import-parse`、`opencodex-import`、`pricing`、`profiles`、`siwc`。名称中的账号、OAuth 或厂商名不代表使用真实服务；是否安全，要检查实际 fixture 的端点、存储和 hooks。

## 新测试加入清单前

1. 读完整文件及导入 fixture，特别是顶层代码、`before`、`after`；不能只看测试名称
2. 把程序、网络、时钟和身份发现做成可注入依赖；使用临时目录、假凭据和 loopback 服务
3. 单独在预加载保护下运行，确认没有靠真实程序缺席或错误被吞掉来通过
4. 把文件加入 `bin/test-local.ts`，并保留必须在真实环境运行的独立断言
5. 涉及路径时在 macOS 验收；涉及真实工具回合时同步维护完整套件，不能只增加一条免责声明

## 如何记录结果

分别记录类型检查、本地白名单、受控桌面假程序、完整真实套件和系统验收。写明运行环境、测试数量、失败与跳过项，以及测试对应的代码版本；不要把旧结果套到后来修改的树上。

例如：“本地白名单通过；真实 Keychain 用例跳过；未运行真实客户端套件。” 比“全部测试通过”更准确。桌面窗口隔离、已有 Keychain 条目授权、launchd 无人交互和真实供应商兼容性，仍需各自的系统验收结果。
